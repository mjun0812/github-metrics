# Configuration / Inputs

Inputs are expressed in a flat key space compatible with the upstream `action.yml`. Parsing is handled by `internal/action.ParseInputs` (env) and `internal/action.CLIFlags` (flags).

## 1. Input resolution order

Because a single binary serves both the Action and the CLI (#646), both go through the same input pipeline. In order of highest to lowest priority:

1. **CLI flags** (`--user` / `--plugin key=value`, etc.)
2. **Values loaded from `--config <path>.yaml`**
3. **`INPUT_<UPPER>` environment variables / `INPUTS` JSON** (generated by the Action runner from `action.yml`)
4. **Default values in code** (held by each plugin's read site and `newInvocation`. Via the Action, `action.yml`'s `default` is passed in as `INPUT_<UPPER>`)

`INPUT_<KEY>` is the input name uppercased with `.` replaced by `_` (e.g. `config_timezone` -> `INPUT_CONFIG_TIMEZONE`). Passing `--no-env` skips the env layer, resolving inputs from CLI flags only.

> The upstream `config_presets` (`--preset`) and the bulk `--plugins` flag do not exist in the current implementation. Plugins are enabled individually via `plugin_<slug>`.

## 2. Input naming scheme

| Prefix                   | Meaning                            | Examples                                                                                                                                       |
| ------------------------ | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `plugin_<slug>`          | Enables a plugin                   | `plugin_languages`, `plugin_achievements`                                                                                                      |
| `plugin_<slug>_<option>` | Plugin option                      | `plugin_achievements_threshold`, `plugin_activity_limit`, `plugin_calendar_limit`                                                              |
| `chrome_<section>`       | Card chrome section gate (boolean) | `chrome_header`, `chrome_activity`, `chrome_community`, `chrome_repositories`, `chrome_metadata`, `chrome_introduction`                        |
| `config_<name>`          | Global settings                    | `config_display`, `config_animations`, `config_timezone`, `config_base64`, `config_order`, `config_octicon`, `config_output`, `config_padding` |

> The "chrome" in `chrome_*` is **a UI term for the card's frame**, unrelated to browsers. The upstream `base=<csv>` / `plugin_base_<section>` forms were removed in v3.0 (#649 / #652) and are no longer accepted.

Other major core inputs (`assets/plugins/core/metadata.yml`): `token` (GitHub PAT), `user`, `repo`, `template`, `filename`, `output_dir`, `combined`, `output_action` (commit / pull-request), `output_condition` (`data-changed`, etc.), `committer_*`, `repositories_skip_private`, `optimize`, `debug_flags`, `github_api_rest` / `github_api_graphql` (endpoints for GitHub Enterprise).

## 3. CLI flags

Flags accepted by `internal/action/cli.go` (`ParseFlags`):

| Flag                            | Corresponding input         | Notes                                         |
| ------------------------------- | --------------------------- | --------------------------------------------- |
| `--user <login>`                | `user`                      |                                               |
| `--template <name>`             | `template`                  | Default `classic`                             |
| `--repo <name>`                 | `repo`                      | Required with `--template=repository`         |
| `--plugin key=value`            | Any input                   | Repeatable. Strongest override                |
| `--output svg\|png\|jpeg\|json` | `config_output`             | Default `svg`                                 |
| `--filename <path>`             | `filename`                  | `-` for stdout. Implies `--combined` when set |
| `--output-dir <dir>`            | `output_dir`                | Per-plugin SVG output (default mode)          |
| `--combined`                    | `combined`                  | Single-SVG mode                               |
| `--skip-private-repo`           | `repositories_skip_private` | Excludes private repositories in all plugins  |
| `--config <path>.yaml`          | ([§4](#4---config-yaml))    |                                               |
| `--dryrun`                      | `dryrun`                    | Suppresses commit / PR side effects           |
| `--no-env`                      | —                           | Ignores the env layer                         |

Only flags the user explicitly passed (`fs.Visit`) override env values. For example, with `INPUT_TOKEN=secret metrics-cli --dryrun`, `INPUT_TOKEN` is left untouched.

## 4. `--config` YAML

`--config` is a way to pass `action.yml`-equivalent inputs via a YAML file (`LoadYAMLConfig`). The nested `plugins:` / `config:` / `committer:` maps are expanded into the flat key space:

```yaml
output: svg # → config_output
config:
  timezone: Asia/Tokyo # → config_timezone
plugins:
  languages: yes # → plugin_languages
  languages_indepth: yes # → plugin_languages_indepth
committer:
  message: "..." # → committer_message
```

Top-level keys are passed through as-is.

## 5. metadata.yml and action.yml

- Input definitions for each plugin / template live in `assets/plugins/<slug>/metadata.yml`. There is no loader that reads these at runtime; type conversion and clamping of inputs are handled at each read site (`pluginutil.ReadIntDefault`, etc.). Templates only load `formats` / `supports` from their own `metadata.yml` at load time (`templates.TemplateMetadata`).
- `action.yml` is auto-generated from these `metadata.yml` files (`internal/tools/gen-action-yml`). The lefthook `action-yml-drift` hook regenerates it on every commit and fails if there is drift. See [`CONTRIBUTING.md`](../CONTRIBUTING.md) for the regeneration procedure.
